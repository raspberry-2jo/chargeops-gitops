### 1.6 결론

1. CSMS는 어떤 경우에도 14~15초 만에 다시 섰다. 회복 시간의 대부분은 충전기 재접속에 걸렸다.
2. 지금의 정상 종료는 연결을 30초 쥐고 있다가 한꺼번에 끊는다. 그래서 강제 종료보다 50초 느렸고, 10,000대 모두 비정상 종료로 기록됐다. Drain(연결을 나눠서 끊기)이 필요하다.
3. 재접속 분산이 없으면 입구(edge)가 TLS 연결 수립을 감당하지 못해 회복이 크게 늦어진다(p95 2.28초). 충전기 재접속 지수 백오프와 분산은 유지해야 한다.
4. DB는 세 경우 모두 여유가 있었다. PgBouncer가 DB 연결을 5개에서 23개까지 늘려 받았고, 대기는 최대 0.83 ms, 트랜잭션이 걸린 채 남은 세션은 0이었다. 부하가 끝나자 연결 수도 스스로 원래대로 돌아왔다.
5. Pod를 늘려도 기존 WebSocket 연결은 옮겨 가지 않는다. 입구가 Pod를 무작위로 고르기 때문에(32.5% ≈ 1/3), 끊어서 옮기는 방식만으로 균형을 맞추려면 거의 전체를 다시 붙여야 한다. 줄일 때는 대량 재접속이 생기고 불균형이 남는다.
6. 따라서 HPA는 지금 넣지 않는다. 먼저 ① 넘치는 Pod가 천천히 끊기, ② 입구 `least_conn`, ③ 종료 때 나눠서 끊기(Drain)를 구현하고, 같은 조건으로 재시험한 뒤 Pod당 연결 수 기준 HPA를 검토한다.

### 1.7 HPA 도입 시 예상 (시험하지 않음, 오늘 실측값으로 추정)

검토한 안: 충전기 10,000대, Pod당 연결 상한 200, HPA 최대 50개 (연결 수 기준).
아래는 실제로 시험한 결과가 아니라 4차 · 5차 실측값을 근거로 한 예상이다.

| 단계 | 예상 | 근거 |
|---|---|---|
| 1. 처음 4개 Pod | 800대에서 4개가 모두 꽉 차고, 그 뒤 충전기는 거절됨 | 상한 200 × 4 |
| 2. HPA 확장 | 거절 → 30초 뒤 재시도가 반복됨. HPA 판단(15~30초) + Pod 기동(14초)으로 한 번에 약 45~60초씩 늦게 따라감 | 4차 Pod Ready 14초 |
| 3. 새 Pod에 새 연결 | 꽉 찬 Pod가 거절하므로 새 Pod의 빈 자리가 채워짐. 상한이 균형을 맞춰 줌 | 5차 "새 Pod 0대" 문제가 상한으로 풀림 |
| 4. 스케줄링 한계 | 워커 CPU 예약이 바닥나 15~20개 이후 Pending. 연결 3,000~4,000대에서 멈춤 | Pod당 CPU 0.2코어 예약, 워커 합계 6코어 |
| 5. 재시도 폭주 | 남은 약 6,000대가 거절될 때마다 TLS 연결 수립을 다시 함. 입구(edge) CPU 100%, 운영 서버 CPU 90% 이상 예상 | 4차 ①: edge 100% · 운영 서버 93% |
| 6. PgBouncer 입구 한도 | 문제 없음. Pod 50개 × 앱 DB 풀 최대 10 = 500으로, PgBouncer `max_client_conn = 2000` 안에 들어감 (2026-10-30 확인) | 실제 DB 연결은 PgBouncer가 25개(20 + 예비 5)로 제한 |

6번 보충: 앱 쪽 연결은 최대 500개까지 늘 수 있지만 DB 쪽은 25개로 고정이다. 재접속이 몰리면 PgBouncer 안에서 기다리는 요청이 늘 수 있다(4차 C에서 대기 최대 0.83 ms). DB 자체는 보호되고, 늘어나는 것은 대기 시간이다.

좋아지는 점:

| 항목 | 지금 (4개 × 약 2,500) | 50개 × 200 |
|---|---|---|
| Pod 1개 장애 시 끊기는 충전기 | 약 2,500대 (25%) | 200대 (2%) |
| 새 Pod에 연결이 가는가 | 안 감 (5차 실측 0대) | 감 (상한이 밀어 줌) |

예상 결론:

1. 상한을 두는 방향은 맞다. 새 Pod가 채워지고, 장애 한 번의 영향 범위가 작아진다.
2. 지금 환경에서 50 × 200은 무리다. 먼저 Pod 스케줄링(15~20개)에서 막히고, 거절된 충전기의 재시도로 입구 CPU가 포화될 것으로 본다. PgBouncer 한도는 여유가 있다.
3. 워커 6코어 기준 현실적인 출발점은 Pod 12개 안팎, Pod당 상한 800~1,000이다.
4. 축소 시험안: 충전기 3,000대, 상한 300, Pod 최소 4 · 최대 12, HPA 목표 Pod당 250.
5. 시험 전 필요한 작업: CSMS 연결 상한 기능(초과 시 종료 코드 1013으로 거절), prometheus-adapter 또는 KEDA로 연결 수 지표를 HPA에 연결, gitops에 HPA 추가와 Rollout replicas ignoreDifferences 설정, Jenkins 빌드와 카나리 배포.

### 1.8 한계

- VM 전부와 부하 발생기가 물리 서버 1대를 나눠 쓴다. ①에서 느려진 원인은 입구(edge)와 부하 발생기가 섞여 있다. 실제 충전기는 각자 따로 있는 기기라 충전기 쪽 CPU는 병목이 아니다.
- 5차의 "천천히 끊기"는 서버가 아니라 가상 충전기 쪽에서 끊어 흉내 냈다. 다시 붙는 경로(edge → 서비스 → Pod)는 실제와 같다.
- 시각 기록 중 "새 Pod 4개 Ready(C)"는 손으로 늦게 남긴 값이라, 쿠버네티스 Pod 기록(Ready 시각)을 기준으로 했다.

### 2.3 Explore에서 쓰는 PromQL

Grafana → Explore → 데이터 소스 Prometheus → 위 표의 시간 범위 → 아래 식을 붙여 넣는다. 간격(Min step)은 15s로 둔다.

| 보고 싶은 것 | PromQL |
|---|---|
| 전체 충전기 연결 | `sum(max by (pod) (chargeops_csms_connections{namespace="ops"} or chargeops_csms_connections{exported_namespace="ops"}))` |
| Pod별 연결 | `max by (pod) (chargeops_csms_connections{namespace="ops"} or chargeops_csms_connections{exported_namespace="ops"})` |
| Ready CSMS Pod | `sum(kube_pod_status_ready{namespace="ops",pod=~"csms.*",condition="true"})` |
| 처리량 (초당 OCPP 메시지) | `sum(rate(chargeops_ocpp_messages_total[1m]))` |
| 응답 시간 p95 | `histogram_quantile(0.95, sum by (le) (rate(chargeops_ocpp_handle_seconds_bucket[1m])))` |
| 실패율 % | `100 * sum(rate(chargeops_ocpp_handler_results_total{result=~"error\|timeout"}[1m])) / sum(rate(chargeops_ocpp_handler_results_total[1m]))` |
| 연결 종료 사유 (건/초) | `sum by (reason) (rate(chargeops_csms_disconnect_total[1m]))` |
| 재접속 (건/초) | `sum(rate(chargeops_csms_reconnect_total[1m]))` |
| VM별 CPU % | `100 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[1m])) * 100` |
| DB 세션 상태 | `sum by (state) (pg_stat_activity_count{datname="chargeops"})` |
| DB 초당 커밋 | `sum(rate(pg_stat_database_xact_commit{datname="chargeops"}[1m]))` |
| 발생 중 알림 (silence 포함) | `count by (alertname) (ALERTS{alertstate="firing"})` |

주의 사항:
- 실패율 식의 `\|`는 표 때문에 넣은 것이다. 실제로는 `|`로 쓴다.
- 운영 서버(물리 호스트) CPU는 Prometheus에 없다. 실험 중 작업 관리자 값(최대 73% · 93% 등)을 그대로 인용한다.
- DB 세션 그래프는 수집기가 db-02 연결까지 함께 세서 위 표(db-01 직접 조회)보다 값이 크다. 보고서에는 1.4의 직접 조회 값을 쓴다.

2. 다음 세 덩어리로 나눠 쓴다.
   - 4차: CSMS Pod 전체 장애 (C 정상 종료 · D 강제 종료 · ① 재접속 분산 0)

   본문에서 반드시 "예상"이라고 밝히고, 실측 결과와 섞지 않는다.
7. 한계(문서 1.8)는 마지막에 짧게 쓴다.
